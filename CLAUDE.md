# Your harness

This file is yours, and it arrives empty on purpose. The rules you hold the
agent to are part of what gets marked, so they should be rules you decided on.

Nothing about the template is recorded here. What the repo ships is explained
where it lives --- `fly.toml`, the `Dockerfile`, the CI workflow and
`spec/README.md` each say what they fix --- and the course website publishes the
[final project brief](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/assessments/final-project/).
What the agent needs to carry from any of it is your call.

## Working in phases

- The build follows numbered phases (PHASE 0–11). Do only the current phase,
  run and check it, report (done / files changed / not done / next), then stop
  until the user says "continue" (继续). Fixing a bug from an earlier phase is
  allowed; deleting a feature to go faster is not.
- No fake buttons, TODO stubs or simulated multiplayer presented as finished.
- Design docs live in `docs/` (`architecture.md`, `game-state.md`,
  `database-schema.md`, `visual-direction.md`). Read the relevant one before
  changing that area; update it in the same change when the design moves.

## Stack constraints (from `fly.toml` / `spec/README.md` — not negotiable)

- One 256 MB machine, one volume at `/data`, no external database. So: one
  Node process (Hono + `ws`), SQLite via `node:sqlite` on `/data`, Vite/React
  client served as static files. No Next.js server, no Supabase.
- `/` returns 200 and `/readme/` serves README.md's headings in server-sent
  HTML. Never delete `spec/invariants.test.ts`.
- Server `.ts` runs directly on Node 24: erasable syntax only (no enums,
  namespaces or parameter properties); imports include the `.ts` extension.

## Game engine rules

- Engine layout: `src/server/engine/` is pure (state + input + time → state +
  cues); `src/server/game/` persists and schedules; `src/client/game/` only
  renders the projected view. Status names live in
  `src/shared/game/scenario01/statuses.ts`; content in `scenario01/`.
- Engine changes need a test in `test/engine.test.ts` (or a new test file) that
  fails without the change; replay determinism must stay green.

- The server is authoritative. Clients send intents (`GameAction`), never
  values: no client-sent dice, fate, phase, round or character.
- All randomness comes from the server's seeded RNG in game state.
- Every action goes through validate → reduce → persist (one SQLite
  transaction) → broadcast, inside the room's serialised queue.
- Hidden information (obsessions, secret messages, allies, dream cards, peeks,
  hidden statuses) is removed by the server projection before sending. Never
  send it and hide it with CSS.
- State is never shown by colour alone: also give text (`READY`, `7 / 12`).
- Mobile first: no horizontal page overflow at 320px, touch targets ≥ 48px.

## Characters and skills

- The 192 characters live in `src/shared/characters/roster/<zodiac>.ts`, one
  file per sign, 16 entries in canonical MBTI order. `pnpm test:unit` proves
  12 × 16 = 192 with no duplicate or missing pair, unique ids, unique titles
  and unique skill names, and runs the static skill checks.
- A skill is data: trigger + target rule + `Effect` primitives. Never write
  per-character code; if a skill can't be expressed, extend the primitives in
  `effects.ts` (the compile-time guard keeps `EFFECT_KINDS` in sync).
- The player-facing `description` is the source of truth for a skill's
  behaviour, and it must match what the effects do. What generic words
  ("reward", "task", "attack") mean in the scenario, and every skill that was
  re-worded to fit, are in `docs/skill-mapping-notes.md`; keep it current.
- A skill may be re-worded only when it depends on a mechanism this scenario
  doesn't have, into a real equivalent here; the notes keep what it was, what
  it is now and why.
- PASSIVE skills fire on their own only if they are a pure gain for their
  holder and there is no strategic reason to save them for a better moment;
  otherwise make them REACTION (the holder is asked).
- `test/abilities-all.test.ts` fires all 192 through the resolver; behaviour
  is tested per mechanism in `test/abilities.test.ts`, not per character.

## Portraits

- The 192 portraits in `public/avatars/` are generated by
  `scripts/avatars/portrait.ts`; never edit an SVG by hand. Change the
  generator, run `pnpm avatars`, and commit the regenerated files.
  `test/avatars.test.ts` fails if a file is stale, missing, duplicated, or
  closer than 3 visible features to any other portrait.
- Each file is self-contained: no scripts, no external URLs, no CSS `var()`
  (presentation attributes don't resolve it in every renderer).

## Testing policy (risk-driven, from PHASE 5)

- Test what the phase changed: rules, state machine, turn flow, abilities,
  Fate/Sanity, hidden information, WebSocket sync, concurrency, reconnect,
  persistence, win/fail. Don't add tests for stable, untouched areas (roster
  counts, avatar files, room codes, create/join, static assets).
- A test must be able to catch a bug that could really happen. No tests for
  count's sake, no duplicate data-swapped variants, nothing TypeScript
  already guarantees, no DOM-structure or CSS tests.
- Abilities are covered per effect / trigger / target type through shared
  handlers, plus data validity for all 192, never one heavy scenario per
  character.
- Reuse the standard fixtures in `test/helpers.ts` (`Table`, `rigNextDie`).
- Mutation-style checks only for new core engine, hidden info/security,
  complex ability execution, concurrent transactions and final win logic.
- Per phase: typecheck + the related unit/spec tests, and a browser
  walkthrough of the shortest path to what changed, with screenshots only of
  new or visibly changed screens. Full suite + full end-to-end walkthrough at
  milestones only: engine complete, scenario winnable, abilities complete,
  final phase.
- On failure, read only the failing test's output (grep for FAIL/Error).
- Balance changes are judged with `pnpm sim` (win rates, Collapse sources,
  idle turns; `--coverage` for abilities), never by feel. The kept logs in
  `docs/simulations/` replay in `test/simulations.test.ts`; if a rule change
  breaks a replay on purpose, regenerate them and say so in the build log.

## Checking UI work

- `pnpm check` (spec against the running app + unit tests) must pass before
  reporting a phase done. Start the app first: `pnpm build && pnpm start`.
- UI changes are checked in a real browser (Playwright, two isolated
  contexts) at 390 and 1280 px, and the screenshots looked at.
  `pnpm ui:walkthrough` is the full end-to-end path for milestones.
  `node scripts/ui-play.ts --until end --phone 320` plays every screen at
  320 px and fails on clipped content or touch targets under 48 px
  (`scripts/lib/layout-check.ts`); a utility like `min-h-11` overrides `.btn`'s
  48 px minimum, so don't use it on buttons.
- Page-level `scrollWidth` hides clipping because `html`/`body` set
  `overflow-x: hidden`; the walkthrough measures elements instead. Grids that
  hold long content need explicit `grid-cols-1` / `minmax(0,1fr)` + `min-w-0`.
- Custom CSS classes go in `@layer components` (base rules in `@layer base`);
  unlayered CSS silently beats Tailwind utilities.
- The display font (Cormorant) needs lining numerals, or 00:17 reads "oo:17";
  this is set globally, don't override it.

## Language

- English is the canonical/default locale. All player-facing text must go
  through the localization layer. New hard-coded player-facing English or
  Chinese strings are not allowed. Layers and glossary: `docs/localization.md`.
  - UI copy: a key in `src/client/i18n/en.ts` and `zh-CN.ts` (`t("lobby.ready")`).
  - Engine text in game state is a `Msg` built with `m``…``` / `ref.*` / `list()`,
    never a sentence or a joined English fragment; give each variant its own
    whole template. Add the Chinese to `src/shared/i18n/zh-CN/messages.ts`.
  - Content (scenario, 192 characters) stays canonical; Chinese is keyed by id.
  - `test/localization.test.ts` fails on a missing key, mismatched
    placeholders, or English left in a Chinese render of a played run.
- Code, comments, commit messages, and docs in the repo are written in
  English, regardless of the language a prompt arrives in.
